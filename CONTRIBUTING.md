# Contributing

Thanks for looking. This page is the process; the README says what the
project is and how to build it, `docs/api.md` records the API decisions that
are settled, and `docs/nodes.md` and `docs/scene-graph.md` explain the two
designs everything else hangs off.

## Before you start

Open an issue first for anything larger than a bug fix with a test. The
port grows one Three example at a time (a "rung", see the README), and a
rung in progress is easy to duplicate from outside. An issue takes a minute
and saves a review that ends in "someone is already on this".

What is welcome, in rough order of how easy it is to merge:

- **Bug fixes with a test.** A failing unit test, or a renderer gate, or
  a Three QUnit test ported into `tests/` that the fix turns green.
- **Ported Three unit tests** (`test/unit` in the three.js checkout) for
  math, core, geometries, animation and loaders. These are cheap, always
  wanted, and often find something.
- **A new rung.** One Three `webgpu_*` example, ported until Three's own
  grader passes on it. Say which example in the issue and what you think
  it needs that is missing; the per-rung notes in `docs/*-progress.md`
  show the shape of the work.
- **API changes.** Read `docs/api.md` first. Breaking changes are batched
  for 0.2.0 and need an issue with the `api` label; a PR that changes a
  public signature without one will be asked to open it.

Out of scope: the WebGL renderer (`renderers/webgl*` in Three), and
anything that needs a backend or platform that cannot be graded. Other
wgpu backends are welcome in principle but only Vulkan on Linux has been
run, so a PR for another one has to bring its own evidence.

## Setting up

The README's *Building* section covers the toolchain, the three.js checkout
the examples and grader read from, and the optional d3-gallery checkout. The
short version:

```sh
git clone --branch r186 --depth 1 https://github.com/mrdoob/three.js ~/src/vendor/three.js
(cd ~/src/vendor/three.js && npm ci)
cargo test -p sdf-text --lib                # sdf-text unit tests; no GPU
cargo test -p three-rs --lib                # three-rs unit tests; no GPU
cargo test --test e2e -- --nocapture        # the grader; needs a Vulkan device
```

The repository is laid out as a bare repo with one worktree per branch;
`CLAUDE.md` describes it. That layout is the maintainer's habit, not a
requirement: a normal clone and a feature branch are fine for a PR.

## Before you open the PR

Run what applies. CI (`.github/workflows/ci.yml`) now enforces `cargo fmt
--all --check`, `cargo clippy --workspace --all-targets -- -D warnings`, the
build and the no-GPU tests on every push to `main` and every PR, so these are
no longer just courtesy checks; the e2e grader remains the manual pre-merge
gate described below, since it needs a real Vulkan adapter and Three's
screenshots that no runner here has yet:

- `cargo fmt` on your new code. Do not reformat lines you did not otherwise
  change; it buries the diff.
- No new clippy warnings in code you wrote, where clippy is available to
  you.
- The no-GPU tests above pass.
- **If the change touches `src/renderer/`, `src/nodes/`, or a material,
  rerun the whole ladder** (`cargo test --test e2e`) on a real GPU before
  asking for review, and say in the PR that you did and what the numbers
  were. Failures on this stack are silent wrong pixels, not errors, so a
  green build proves nothing; the grader is the only judge. The graded
  examples table in the README is the reference; if a number moves, the
  PR explains why.
- If the change is user-visible, add a line under *Unreleased* in
  `CHANGELOG.md` (once #19 lands; until then, the PR description carries
  it).

Things the grader assumes and reviewers will look for:

- The grader is Three's own `test/e2e/image.js`, unmodified, with Three's
  threshold. Do not loosen it, do not write a second comparator.
- Nothing derived from a reference screenshot goes in the tree: no
  reference bytes, no hard-coded pixels, no per-example colour fudges.
- Shaders come from the node system. A rung's WGSL is generated by the
  `NodeBuilder` port from the example's node graph, the way
  `WebGPURenderer` does it, and is checked against Three's dump for that
  example. Hand-written WGSL is not a shortcut a rung can take.
- Where the port reproduces a Three quirk bit-for-bit on purpose, or
  deliberately diverges, say so in a comment and in `docs/nodes.md`'s
  divergence list. Both already happen; the notes are what stop the next
  person "fixing" them.

## Commits and merging

Subjects are `area: what it does`, lower case after the colon, no trailing
full stop, under about 70 characters, as in `renderer: key the per-draw
caches on ids, not addresses` or `rung 8: the six-face point shadow pass`.
The area is the directory or crate (`renderer`, `nodes`, `lines`,
`sdf-text`, `e2e`, `docs`, `README`) or the rung. The body says why, and
names the issue.

Branches are merged with `git merge --no-ff`, so every branch is a merge
commit with two parents and shows as a branch in the graph; history inside
the branch is kept as it was reviewed, not squashed. Rebase your branch
onto `main` if it has drifted; do not merge `main` into it, which braids
the graph instead of leaving one lobe. One PR does one thing; a
rung PR is the exception, and its commits should still read as steps.

## Reporting a bug

The most useful bug report for a renderer is the example name, your GPU,
driver and OS, and the `actual.png` and diff strip from
`target/e2e/<example>/`. A scene that renders wrong with no panic is the
normal failure mode here, so "it looks different" with a picture is a
complete report.
