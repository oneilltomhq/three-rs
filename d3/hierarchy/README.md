# d3-hierarchy (Rust)

A port of [d3-hierarchy](https://github.com/d3/d3-hierarchy) 3.1.2
(`~/src/vendor/d3-hierarchy`, tag 7bea49e) to Rust. f64 throughout, and the
same operation order as the JS, so results match to the bit. No dependency on
three-rs; `serde_json` only.

Stage 2 of the d33 ladder: d33 ports d3 gallery examples to Three.js keeping
d3's layout half as a JS dependency; this crate is that layout half in Rust,
with d3's own tests as the grader.

## Node representation

The JS is built on mutable node objects with `parent` pointers, shared
identities (`links()` returns the very node objects, `a.parent === b.parent`)
and dynamically added layout properties. The Rust shape is an **arena**:

```rust
pub struct Tree { pub nodes: Vec<Node>, pub root: usize }
pub struct Node {
    pub data: serde_json::Value,
    pub depth: usize, pub height: usize,
    pub parent: Option<usize>, pub children: Option<Vec<usize>>,
    pub value: Option<f64>, pub id: Option<String>,
    pub x: f64, pub y: f64,                            // cluster, tree
    pub x0: f64, pub y0: f64, pub x1: f64, pub y1: f64, // partition, treemap
    pub r: f64,                                        // pack
}
```

- `parent`/`children` are `usize` indices into `Tree::nodes`. Node identity is
  the index, so d3's `===` comparisons become `==` on indices.
- `children: None` is JS `undefined` (a leaf); d3 distinguishes "no children"
  from "empty children" in places (`count`, `treemap`), so `Some(vec![])` is
  kept distinct.
- Layout fields always exist and default to 0, rather than being absent until a
  layout runs. `value` stays `Option` because d3 leaves it `undefined` until
  `sum`/`count` and several algorithms branch on that.
- `data` is `serde_json::Value` rather than a generic `D`. Every d3 test and
  every d33 input (flare.json, flare.csv) is JSON, and the children/value
  accessors are then plain closures over `&Value`. A generic `D` is the obvious
  later extension; nothing in the algorithms depends on the choice.
- Traversal is exposed twice: `order_each` / `order_before` / `order_after`
  return the visit order as `Vec<usize>` (built with the same stack operations
  as the JS, so the order is identical), and `each*` call a closure over that
  order. The algorithms use the `order_*` form because a callback cannot hold
  `&mut Tree` while the traversal does.

## Tests

`tests/` holds ports of d3's own tape tests, expectations verbatim, one Rust
test per `it(...)`, named after it. Where d3 has no test for a module (see
below) the expectations are generated by running the vendor JS itself; the test
file says so and names the command.

### Modules

| module | source | tests |
| --- | --- | --- |
| `node` | `src/hierarchy/*.js` | `tests/hierarchy.rs` (11) |
| `cluster` | `src/cluster.js` | `tests/cluster.rs` (8) |
| `tree` | `src/tree.js` | `tests/tree.rs` (9) |
| `partition` | `src/partition.js` | `tests/partition.rs` (8) |
| `pack` | `src/pack/*.js` | `tests/pack.rs` (6) |
| `treemap` | `src/treemap/*.js` | `tests/treemap.rs` (28) |
| `stratify` | `src/stratify.js` | `tests/stratify.rs` (30) |

100 tests. `cargo test --workspace` from the worktree root runs these and the
three-rs crate's own tests.

d3-hierarchy 3.1.2 ships **no** `test/cluster-test.js`, `test/tree-test.js` or
`test/partition-test.js` (its `test/` holds only `data/`, `hierarchy/`, `pack/`,
`treemap/` and `stratify-test.js`). For those three modules the expectations
were generated by running the vendor JS itself and pasted in as literals; each
test file's header gives the exact `node` command. Everything else is a verbatim
port of the tape test.

### Not ported, with reasons

- `d3.hierarchy(Map)` / `mapChildren`, and the `children: new Set([...])` half
  of `test/hierarchy/index-test.js`: JS-only data shapes that
  `serde_json::Value` cannot express. The array form of the same assertion is
  ported.
- `test/pack/bench-enclose.js`, `find-bugs.js`, `find-enclose-bugs.js`,
  `find-place-bugs.js`: a benchmark and three random fuzzers, not tape tests.
- `test/stratify-test.js`, 5 of 38 `it()` blocks: the two "accepts an iterable"
  cases (input is a JS `Set`; with `&[Datum]` they are identical to the array
  cases that precede them), the second "allows the id to be undefined for leaf
  nodes" (datum is `{parentId: {toString(){…}}}`), and the two "tests that id is
  a function" cases (d3's `optional()` throwing on a non-function). Listed again
  at the foot of that test file.
- `test/treemap/index-test.js`, 3 cases: "coerces the specified round to
  boolean" (`!!"yes"`), "coerces the specified size to numbers" (`+x[0]` on a
  string), "makes defensive copies" (`[f64; 2]` is `Copy`, there is no aliasing
  to defend against).
- `test/treemap/flare-test.js`, both cases: they need `d3-dsv` CSV parsing plus
  `stratify`, and `flare-phi.json` / `flare-one.json` are in the D3 3.x
  `x/y/dx/dy` shape with a reverse-children fixup. The tiling itself is covered
  by the seven tiling test files; worth revisiting now that `stratify` exists.
- Single assertions dropped inside otherwise-ported tests: function and
  prototype identity (`root instanceof hierarchy`, `t.tile() === squarify`,
  `s.id() === foo`) and getter-overloading asserts, which test JS's
  `arguments.length` API rather than behaviour. The Rust API has separate
  setters and getters, so there is nothing to assert.

### Divergences from d3 found

- `leaf_left`/`leaf_right` in `cluster`: the JS `while (children = node.children)`
  treats an empty array as truthy and then throws on `undefined.children`; the
  Rust version ends the descent on `Some(vec![])`. Unreachable for trees built
  by `hierarchy()`.
- `squarify` uses Rust's `f64::max`, which ignores NaN where JS's `Math.max`
  propagates it. Only reachable with a NaN node value, which `sum` already
  coerces to 0.
- `stratify` number→string id coercion goes through `serde_json`'s formatting,
  so a float-typed whole number would give `"1.0"` where JS gives `"1"`. No test
  reaches it; integer and non-integer ids both match.
- `stratify` leaves unreachable arena entries behind when the imputed root is
  collapsed, so `tree.nodes.len()` is not the tree's node count. Traversals all
  start from `root`, so nothing observable changes.
- `resquarify` state is shared between instances derived via `ratio()`, because
  in d3 the state lives on the node (`parent._squarify`), not on the layout.
